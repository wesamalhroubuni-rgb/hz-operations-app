# ADR-0006: File storage and the photo upload flow

- **Status**: Accepted; amended in part by
  [ADR-0008](0008-offline-storage-sync-and-conflicts.md) (2026-10-27: attachment `clientId`,
  photos declared at a log's create accepted for 30 days after the edit window, renew and complete
  of a started upload allowed for 30 days, which removes the limitation that an upload could not
  complete after the window)
- **Date**: 2026-10-17
- **Phase**: 4 (Mobile worker app)
- **Amends**: [ADR-0005](0005-authorization-model.md) in part (a `pending` attachment is visible
  only to its uploader; finding F5, the client-chosen `storageKey`, is resolved)

## Context

Workers attach photos to work logs from their phones. Phase 2 left a `FileStorage` interface with
no provider and let the client choose the attachment's `storageKey`, which ADR-0005 accepted only
until Phase 4 (finding F5: a duplicate key answered 409 even for an attachment the caller could
not see). The owner's Phase 4 prompt (`docs/prompts/phase-4.md`) asked for:

- an S3-compatible provider behind the Phase 2 interface, with MinIO in Docker Compose for
  development, bound to `127.0.0.1`;
- short-lived pre-signed upload URLs, or uploads through the API if that is safer, with the choice
  justified here;
- storage keys generated by the API, never by the client; images only, with a configurable size
  limit; HEIC/HEIF handled as we decide;
- downloads through short-lived signed URLs, only for users who may see the parent work log;
- thumbnails or resized variants for lists.

Phones are on mobile networks, photos are a few hundred kilobytes to a few megabytes, and the API
runs as a single small Node process today.

## Decision

### Provider

`FileStorage` moved to the platform (`apps/api/src/platform/storage/file-storage.ts`, no
Operations imports) and is implemented by `S3FileStorage` (`s3-file-storage.ts`) on the AWS SDK v3
(`@aws-sdk/client-s3`, `@aws-sdk/s3-request-presigner`). It works with any S3-compatible service:
MinIO in development, S3 or another provider in production. It uses **two clients**: `internal`
on `STORAGE_ENDPOINT` for the API's own calls, and `signer` on `STORAGE_PUBLIC_ENDPOINT`, used only
to sign URLs. A SigV4 signature covers the `Host` header, so a signed URL must name the address the
phone or browser connects to (in a phone test, the PC's hotspot address); signing makes no network
call.

**Start-up.** In `development` and `test` a missing bucket is created (private). If the storage is
unreachable there, the API logs a warning and boots; the upload endpoints answer 503 until it is
back. In `production` the bucket must already exist: a missing or unreachable bucket stops the
boot. The bucket is never public. Production also refuses a non-`https://`
`STORAGE_PUBLIC_ENDPOINT` and a placeholder or weak `STORAGE_SECRET_ACCESS_KEY`.

**MinIO in Docker Compose** (`docker-compose.yml`, service `minio`): MinIO stopped publishing
official container images in 2025, so the service uses the community build
`alpine/minio:RELEASE.2025-10-15T17-29-55Z`, **pinned by digest as well as tag** (a tag can be
moved to other content, a digest cannot). The image runs as an unprivileged user; data is in the
`minio_data` volume at `/home/minio`. The health check uses `wget`; the image has no `mc` client,
so there is no bucket-init container (the API creates the bucket). The API port binds to
`MINIO_BIND_HOST` (default `127.0.0.1`; `0.0.0.0` only for a phone test) and the console to
`127.0.0.1` always.

### Upload flow: direct pre-signed PUT, verified on completion

1. **Start**: `POST /work-logs/:id/attachments` with `{ fileName, mimeType, sizeBytes }`
   (`mimeType` is `image/jpeg` or `image/png`; `sizeBytes` at most `UPLOAD_MAX_BYTES`, default
   10 MiB). The caller must be allowed to change the log's attachments (the archive rule of the
   log). The API creates a `pending` attachment with a key it chooses,
   `org/<organizationId>/work-logs/<workLogId>/<random uuid>.<jpg|png>`, and answers
   `{ attachment, upload: { url, method: 'PUT', headers: { Content-Type }, expiresAt } }`. The URL
   lives `UPLOAD_URL_TTL_SECONDS` (default 300) and **signs both `Content-Type` and
   `Content-Length`**: the storage refuses any other type or size.
2. **PUT**: the client sends the bytes straight to the storage with exactly the returned headers.
3. **Complete**: `POST /attachments/:id/complete`. The API stats the object, reads at most
   `UPLOAD_MAX_BYTES`, checks the magic bytes against the declared type, **decodes the whole image**
   (at most 24 megapixels), and **re-encodes** it (EXIF orientation applied, all metadata dropped,
   nothing after the image kept; JPEG at quality 85 with mozjpeg, or PNG) to a new key
   `<upload key without extension>.<nonce>.verified.<ext>`, for which no upload URL was ever
   signed. It writes a 320 px JPEG thumbnail at `<verified key>.thumb.jpg`, switches the row's
   `storageKey` to the verified key, stores width, height, and the real size, marks it `ready`, and
   deletes the upload object after the commit. A file that fails a check is deleted and answered
   with 422 (`details[0].path` is `file`, the message one of `not_an_image`, `type_mismatch`,
   `corrupt`, `too_many_pixels`); the attachment stays pending so the client can upload again.
4. **Renew**: `POST /attachments/:id/upload-url` gives a pending attachment a fresh URL (expired
   or failed upload). The phone keeps a checkpoint per photo, so a retry renews the same attachment
   instead of creating another.

Image work is `images.ts` (on `sharp`, prebuilt binary, no install script) behind `ImageProcessor`,
which allows **2 decodes at once per process**; a caller that waits more than 30 seconds for a slot
gets 503. Concurrent completions of one attachment in one process run one after the other
(`KeyedSerializer`), so the second finds it ready and decodes nothing; across instances a
conditional update decides the winner and the loser removes its copies.

Status codes: 400 size or type in the body; 403 the log's rule forbids it; 404 the log or
attachment is not visible; 409 archived log or attachment, the cap of **20 non-archived
attachments per log** (checked under a per-log advisory lock), or "not uploaded yet"; 422 bad
content; 429 more than 60 starts, 60 completions, or 60 renewals per user in 10 minutes (per
process, through the platform `RATE_LIMITER`); 503 storage down or no decode slot.

### Visibility and downloads

- A `pending` attachment is visible **only to its uploader** (404 and absent from lists for
  everyone else); a `ready` one to whoever can see the parent log (`attachment.rules.ts`).
- The API never returns a storage key. Signed `url`, `thumbnailUrl`, and `urlsExpireAt` are
  computed only for **ready, non-archived attachments loaded through the caller's visibility**
  (`AttachmentsService.present`), with `DOWNLOAD_URL_TTL_SECONDS` (default 300) and an `inline`
  `Content-Disposition` carrying a sanitised file name. The phone refetches before they expire.

### Events, cleanup, and purge

- Outbox and audit events: `attachment.upload_started`, `attachment.completed`,
  `attachment.archived`, `attachment.upload_expired`. They carry the attachment without keys or
  URLs.
- **Cleanup** (`attachment-cleanup.service.ts`, hourly in each API process, first run one hour
  after start): a pending attachment older than 24 hours is archived first (only if still pending,
  event `attachment.upload_expired`, actor `system`), then its object is deleted. Claiming first
  means a phone that completes in between keeps its photo.
- **Purge**: the upload object of every attachment archived while still pending is deleted once its
  upload URL can no longer be used (`archivedAt + UPLOAD_URL_TTL_SECONDS`), retried by each hourly
  run for 48 hours after that point, with no marker column (deleting a missing object succeeds).
- Archiving a `ready` attachment keeps its bytes and thumbnail (history); no URL is signed for it.

### HEIC/HEIF

Not accepted by the API. The phone converts every photo to JPEG before upload (long edge 1600 px,
quality 0.7, metadata dropped), which turns HEIC from iPhones into JPEG.

## Reasons

- **Direct PUT instead of proxying through the API.** Photo bytes never pass through the Node
  process on the way in, so a slow mobile upload does not hold an API connection or memory, and the
  API scales with requests rather than bandwidth. Signing `Content-Length` and `Content-Type` lets
  the storage itself enforce the size and type before the API sees anything. What proxying would
  have given (the API sees the bytes before they are accepted) is recovered by verifying on
  completion: nothing is ever served that the API has not decoded and re-encoded.
- **Re-encode to an API-only key.** The upload URL stays valid for its lifetime even after
  `complete`; serving the uploaded object would let a client replace a verified photo with anything
  during that window (security review finding M1). Serving a re-encoded copy under a key nobody can
  PUT to closes that window and also strips EXIF (including GPS) and polyglot payloads.
- **API-generated keys** remove F5 and make keys unguessable and organization-prefixed.
- **Signed downloads only after the visibility check** keep the storage private and reuse the
  existing access rules instead of a bucket policy per user.
- **Limits** (decode concurrency, pixel cap, attachment cap, per-user rate limits) bound what one
  user or a stuck client can cost the process (finding M2).

## Tradeoffs

- **Two round trips more than a proxied upload** (start, PUT, complete), and the client must
  handle three failure points. The shared `uploadAttachment` helper and the checkpoint hide this
  from the screens.
- **Orphan bytes on ready attachments.** After `complete`, a client that still holds the upload URL
  can PUT again within its lifetime; those bytes are never served, but no job removes them (the
  purge covers only attachments archived while pending). Harmless, costs storage. A purge marker
  column would fix it (Phase 8).
- **Per-process limits.** The decode limit and the upload rate limits are in memory, per process;
  several API instances each allow their own share. A shared limiter is Phase 8.
- **Purge window of 48 hours.** A storage outage longer than that leaves upload bytes of archived
  pending attachments behind.
- **A lost `startUpload` answer** (the request succeeded but the phone never got the response) can
  leave a second pending attachment, invisible to everyone but the uploader, until the cleanup
  archives it after 24 hours.
- **An author cannot complete an upload after the edit window closes**, because `complete` uses
  the same rule as starting it. Accepted: photos are normally sent seconds after the log.
- Decoding costs CPU and memory on the API (bounded as above).
- The MinIO image is a community build; it is for development only and needs replacing or building
  from source before anything depends on it (Phase 8).

## Alternatives considered

| Alternative                                        | Why not                                                                                                                                                       |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Upload through the API (multipart to a Nest route) | Every photo byte through the Node process: memory and connections held for the length of a mobile upload. The verification on complete gives the same safety. |
| Serve the uploaded object after checking it        | Leaves the post-complete overwrite window open (M1) and keeps EXIF and appended data.                                                                         |
| Pre-signed POST policy instead of PUT              | Also works; PUT with signed headers needs no form encoding on the phone and pins an exact size rather than a range.                                           |
| Public bucket or long-lived URLs                   | Anyone with a link could see a photo forever; no per-user check.                                                                                              |
| Accept HEIC on the server                          | Needs a HEIF decoder in `sharp` and browsers cannot show it; converting on the phone is simpler and makes files smaller.                                      |
| A local-disk `FileStorage` for development         | A second implementation to keep in step; MinIO behaves like production S3, including signed URLs.                                                             |
| Official MinIO image or a Bitnami image            | Official images are no longer published; the community image pinned by digest is the smallest working option for development.                                 |
| A bucket-init container running `mc`               | The pinned image has no `mc`; the API creating the bucket in development is one less moving part, and production must create it deliberately.                 |

## Consequences

- Never accept a storage key from a client; keys come from `attachmentStorageKey` and
  `verifiedKeyOf` in `attachments.service.ts`.
- Signed URLs are produced only by `AttachmentsService.present` for rows loaded through
  `attachmentVisibilityWhere`.
- Outbox and audit payloads never contain a key or a URL.
- A phone test needs `STORAGE_PUBLIC_ENDPOINT` set to an address the phone can reach and MinIO
  bound to the network (README); the API must be restarted after the change, because signed URLs
  name the endpoint the API started with.
- A web upload (Phase 6) needs a CORS rule on the bucket.
- Phase 8: a real S3 provider with a bucket policy and a scoped key, a shared rate limiter, a purge
  marker for orphan bytes, retention and erasure of photos, and a replacement for the community
  MinIO image.
